# T1685.005 — Clear Windows Event Logs

## Lényeg

A támadó a *már keletkezett* Windows eseménynapló-bejegyzéseket törli — jellemzően a Security, System vagy Application napló egészét —, hogy eltüntesse a korábbi tevékenységének (bejelentkezés, folyamatindítás, szolgáltatás-telepítés) nyomát. Ez az [[T1685.001 - Disable or Modify Windows Event Log]] "ellenkező irányú" párja: az .001 *megelőzi* az esemény keletkezését, ez az altechnika a *már megtörtént* esemény rögzítését tünteti el utólag.

Ez a legkevésbé rejtett anti-forensics lépés a T1685 alatt: egy hirtelen üres eseménynapló (vagy a napló törléséről szóló, ironikus módon *magát* naplózó 1102-es esemény) önmagában erős, azonnal észlelhető gyanújel — nincs olyan legitim IT-folyamat, ami rutinszerűen teljesen kiüríti a Security naplót éles gépen.

> [!quote] MITRE definíció
> Adversaries may clear Windows Event Logs to hide the activity of an intrusion.

## Hogyan csinálják a gyakorlatban

### `wevtutil` — natív parancssori eszköz

A legelterjedtebb módszer, mert semmilyen külső binárist nem igényel: a `wevtutil cl` (clear-log) parancs egyetlen híváson belül kiüríti a megadott naplót.

```cmd
wevtutil cl Security
wevtutil cl System
wevtutil cl Application
```

### PowerShell cmdlet-ekvivalens

```powershell
Clear-EventLog -LogName Security
```

vagy a régebbi, WMI-alapú forma:

```powershell
Get-WmiObject Win32_NTEventlogFile | Where-Object {$_.LogfileName -eq 'Security'} | Invoke-WmiMethod -Name ClearEventLog
```

### GUI (Event Viewer)

Az `eventvwr.msc`-ben a "Clear Log..." menüpont ugyanezt a hatást éri el, parancssor nélkül — csak a keletkező 1102-es esemény (és a törlést végrehajtó felhasználó neve, ha a GUI-t használta) árulja el.

**Mi váltja ki a gyakorlatban:** legitim körülmények között gyakorlatilag nem fordul elő teljes napló-törlés — a leggyakoribb "hasonló, de ártatlan" eset egy lemezterület-kezelési szkript, ami a napló *méretét* korlátozza (`wevtutil sl` a `maxsize` paraméterrel), nem a tartalmát törli; ez a két művelet a `CommandLine`-ban jól megkülönböztethető (`cl` vs. `sl`).

## Mitigáció

- **A törlési esemény maga (1102/104) az egyetlen valós védelmi vonal itt** — a `wevtutil cl` maga is generál egy "Eseménynapló törölve" bejegyzést (Security 1102, System 104), ami a törlés pillanatában még a naplóban van, mielőtt a törlés végrehajtódna, vagy — ha távolról továbbítva van — már el is hagyta a hosztot.
- **Windows Event Forwarding / valós idejű log-továbbítás** (ebben a pipeline-ban: a Splunk Universal Forwarder) teszi ezt a védelmet ténylegesen hatásossá: ha az esemény a törlés pillanatában már egy külső, a támadó számára nem elérhető rendszeren (a Splunk indexen) van, a helyi törlés a bizonyítékot már nem tudja eltüntetni — csak a helyi másolatot.
- **Jogosultság-korlátozás** (a Security napló törléséhez adminisztratív jogosultság kell) nem szünteti meg az előfeltételt olyan behatolásnál, ahol a támadó már admin — csak azt jelenti, hogy alacsonyabb jogosultsági szinten ez az altechnika nem elérhető.

## Detekciós stratégia

### Szükséges telemetria

| Adatforrás | Típus | Megjegyzés |
| ---------- | ----- | ---------- |
| Windows Security 1102 / System 104 | Log | a törlés natív, közvetlen jele — **nincs ebben a pipeline-ban feldolgozva** |
| Sysmon EID 1 (ProcessCreate) | Process | `wevtutil cl`/`Clear-EventLog` parancssori mintája — elméletileg elérhető, jelenleg nincs rá szabály |

### Detekciós logika

**Ez az altechnika ténylegesen nincs lefedve.** DETECT-2026-0016 korábban `attack.t1685.005`-re is tagelve volt, de a `ScriptBlockLogging`/`ModuleLogging` policy-kulcsokra és a hozzájuk tartozó `Remove-Item`-mintára illeszkedik — ez a naplózás *megelőző letiltása* ([[T1685.001 - Disable or Modify Windows Event Log]]), nem a már meglévő bejegyzések *utólagos törlése*. Bjorn 2026-09-27-én megerősítette ezt a jegyzet saját elemzésével egyezően, és a `.005` tag eltávolításra került a szabályból. A `wevtutil cl`/`Clear-EventLog` mintára továbbra sincs külön selection egyik szabályban sem — jelenleg egyetlen szabály sincs erre az altechnikára tagelve.

A technikailag helyes detekció két, ebben a repóban jelenleg hiányzó út egyikén épülne:

- **Natív, legerősebb jel: Security 1102 / System 104 közvetlen figyelése** — ez a törlés tényét magától a Windows-tól kapja, függetlenül attól, hogy `wevtutil`, `Clear-EventLog` vagy a GUI hívta-e.
- **Kiegészítő, folyamatalapú jel: `wevtutil cl`/`sl` és `Clear-EventLog` mintája a `CommandLine`-ban** (Sysmon EID 1) — gyengébb, mert csak a parancssoros utat fedi, a GUI-s törlést nem.

### False positive források

- Lemezterület-kezelő karbantartó szkriptek, amik a napló *méretét* állítják (`wevtutil sl ... /ms:`), nem törlik — a `cl` és `sl` alparancsok `CommandLine`-ban jól elkülöníthetők
- Naplórotációs automatizáció régi, archivált rendszereken (ritka, éles domain-környezetben szinte sosem legitim a teljes törlés)

## Kapcsolódó szabályok

*Jelenleg nincs olyan szabály, ami ténylegesen ezt az altechnikát (naplótörlés) fedné, és nincs is rá tagelve — lásd a Detekciós logika szakaszt a DETECT-2026-0016 2026-09-27-i tag-javításáról.*

**Nem fedett:**
- **`wevtutil cl <log>` / `Clear-EventLog`** — nincs selection egyik szabályban sem erre a konkrét parancsmintára
- **Security 1102 / System 104 esemény natív figyelése** — ez a technika legerősebb, leginkább hamisítatlan jele, és a pipeline jelenleg nem dolgozza fel ezeket az EventCode-okat
