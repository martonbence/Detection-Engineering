# T1110.001 — Password Guessing

## Lényeg

A klasszikus "brute force" szűk értelemben: a támadó **egy (vagy néhány) ismert fiókot** céloz, és ellene **sok, szisztematikusan generált vagy listából vett jelszót** próbál, közvetlenül egy élő hitelesítési szolgáltatás ellen. Ellentétben a [[T1110.002 - Password Cracking]]-gal, itt nincs előzetesen megszerzett hash — a támadó a hitelesítési szolgáltatást magát használja "orákulumként": minden próbálkozásra kap egy igen/nem választ.

Ez a legkockázatosabb az online altechnikák közül a támadó szempontjából: mivel egyetlen fiókra koncentrál sok próbát, egy szigorú fiók-lockout házirend gyorsan lezárja — ez az oka, hogy a `.003` (Password Spraying) létezik egyáltalán, pont ennek a kockázatnak a megkerülésére.

> [!quote] MITRE definíció
> Adversaries with no prior knowledge of legitimate credentials within the system or environment may guess passwords to attempt access to accounts.

## Hogyan csinálják a gyakorlatban

### Hydra hálózati szolgáltatás ellen

A `Hydra` a legelterjedtebb online brute-force eszköz, tucatnyi protokollt támogat (SSH, RDP, SMB, FTP, HTTP form, adatbázisok). Egy ismert felhasználónév (`-l`) és egy jelszólista (`-P`) ellen fut:

```bash
hydra -l administrator -P /usr/share/wordlists/rockyou.txt rdp://10.10.10.10
```

RDP-nél a valós gyakorlatban szinte mindig fojtva (egyetlen szál, `-t 1`) futtatják, mert a Windows RDP-nél a lockout és a lassú válaszidő is korlátoz:

```bash
hydra -t 1 -V -f -l administrator -P /usr/share/wordlists/rockyou.txt rdp://10.10.10.10
```

A logban a célgépen (vagy a DC-n, ha domain-fiók) sorozatban jelenik meg a **4625** ugyanarra a `TargetUserName`-re, jellemzően egyetlen forrás-IP-ről.

### CrackMapExec/NetExec SMB/WinRM ellen, már domain-ismerettel

Miután a támadó egy AD-környezetben már ismer néhány felhasználónevet (pl. enumerálásból), a `CrackMapExec` (újabban `NetExec`) egy jelszólistát egyszerre több host ellen is próbál:

```bash
crackmapexec smb 10.10.10.0/24 -u administrator -p /usr/share/wordlists/rockyou.txt
```

Ez technikailag még mindig **egy fiók × sok jelszó**, csak a célgépek száma nő — a `TargetUserName` mezőben így is ugyanaz a fiók ismétlődik, csak több `ComputerName`/DC-n.

**Mi váltja ki a gyakorlatban:** egy felhasználó, aki elfelejtette a jelszavát és többször egymás után újrapróbálkozik (jellemzően kevés kísérlet, egyetlen forrásból); egy hibásan konfigurált szolgáltatás/ütemezett feladat, ami egy elavult jelszóval végtelenül újrapróbálkozik (ez a leggyakoribb, és sokszor a legkitartóbb FP-forrás valós SOC-okban); egy sebezhetőség-vizsgáló eszköz, ami alapértelmezett hitelesítő adatokat tesztel.

## Mitigáció

- **Fiók-lockout házirend** — ez az egyetlen kontroll, ami a `.001` **előfeltételét közvetlenül megszünteti**: alacsony küszöbnél a fiók pár rossz próbálkozás után zárolódik, a támadónak nincs tovább mit próbálnia. Ez a `.001`-nél tényleg működik — szemben a `.003`-mal, ahol pont ezt kerüli meg a támadó.
- **MFA külső elérésű szolgáltatásokon** — akkor is hatásos, ha a jelszót véletlenül eltalálja: a helyes jelszó önmagában nem elég.
- **Feltört/gyenge fiókok proaktív cseréje, `auditpol`-alapú monitorozás bekapcsolása** — nem szünteti meg az előfeltételt, de ez teszi lehetővé a detekciót egyáltalán.
- **Fontos hátrány, amit érdemes fejben tartani:** egy nagyon alacsony lockout-küszöb maga is visszaélhető — egy támadó szándékosan, ismert felhasználónevekre futtatott hibás próbákkal ki tud zárni legitim felhasználókat (ez már [T1531-szerű](https://attack.mitre.org/techniques/T1531/) DoS, nem ez a technika, de a küszöb-hangolásnál ez a tervezési feszültség mindig jelen van).

## Detekciós stratégia

### Szükséges telemetria

| Adatforrás | Típus | Megjegyzés |
| ---------- | ----- | ---------- |
| Windows Security 4625 | Logon (Failure) | a fő jel — `auditpol`: Logon/Logoff → Audit Logon (Failure) |
| Windows Security 4771 | Kerberos Auth (Failure) | ha az eszköz Kerberos-alapú (pl. kerbrute-szerű) próbálgatást futtat, nem NTLM-et |
| Windows Security 4776 | Credential Validation (Failure) | NTLM-alapú próbálgatásnál |
| Windows Security 4624 (Type 3) | Logon (Success) | a sikeres találat — korrobációra, ha a sok hiba után egy siker jön |

### Detekciós logika

A minta **egy fiókra vetített, magas hibaszám rövid időablakban** — `stats count by TargetUserName, src_ip` jellegű aggregáció, küszöbbel (pl. N hiba M percen belül ugyanarra a fiókra). A `SubStatus` mező segít kiszűrni a szomszédos, de más jelenséget: `0xC000006A` (rossz jelszó) a valódi próbálgatás jele, `0xC0000064` (nem létező felhasználó) inkább felhasználónév-enumerációra utal, nem erre a technikára.

Domain-fiókoknál a DC-n (4625/4771/4776) sokkal megbízhatóbb jel, mint a célgépen — utóbbin a helyi Biztonsági log csak akkor látja, ha helyi fiók ellen fut a próbálgatás, ami ritkább AD-környezetben.

### False positive források

- **Elfelejtett jelszó, ismételt kézi próbálkozás** — jellemzően alacsony számú (2-5) kísérlet, egyetlen forrásból, gyakran ugyanabból az irodai IP-tartományból, mint a felhasználó szokásos munkamenete
- **Elavult hitelesítő adattal futó szolgáltatás/ütemezett feladat** — ez a leggyakoribb, tartósan ismétlődő FP: egy jelszóváltás után egy service account vagy egy mapped drive/ütemezett job a régi jelszóval próbálkozik, gyakran percenként, napokig — ez a mintázat (állandó forrás, állandó fiók, állandó ütem) jól elkülöníthető egy valódi támadástól, ami tipikusan gyorsabb és rövidebb életű
- **Sebezhetőség-vizsgáló/compliance-scanner** — alapértelmezett hitelesítő adatokat próbáló, ismert scanner-IP-kről induló forgalom, allowlistelhető
