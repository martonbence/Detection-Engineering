# Threat Model

Scope: this document covers risks in *this repo's own pipeline and detection content* — not the security posture of whatever environment a deployed Sigma/SPL rule is meant to protect. It's grounded entirely in what `.github/workflows/*.yml` and `scripts/` actually do; nothing here is a hypothetical "what a mature detection-engineering shop should also worry about" unless the code shows it's actually a live concern.

## In scope

### Rule quality and false-positive risk
- **Schema validity is enforced; logical soundness is not.** `scripts/validate/validate_sigma.py` gates every rule against `docs/schemas/sigma_schema.json` (Draft-07), but that only checks structure — required fields, correct types, valid enum values. It does not check whether a `detection:` block's filters reference fields the declared `logsource` would actually produce, whether `falsepositives:` is realistic, or whether a `custom.splunk.raw_query` string is syntactically valid SPL beyond what Splunk itself rejects at deploy time. That judgment layer is explicitly the job of the `detection-content-reviewer` Claude Code subagent, not CI.
- **Pass/Fail is evidence of "the search fired once," not "the rule is good."** `pass_fail_eval.py` confirms a saved search matched events after a specific Atomic Red Team execution. A rule can pass this check and still be too broad (high false-positive rate in real traffic) or too narrow (only catches the exact atomic test's command line, not the technique in general) — the pipeline has no signal for either.
- **MITRE coverage gaps** are measurable (`outputs/reports/mitre_technique_map.json`, `navigator_layer.json`, and the Navigator view in `docs/index.html`) but not enforced — nothing blocks a merge for leaving a tactic uncovered. Coverage-gap analysis is currently a human/`ideation`-agent activity, not a CI gate.
- **Duplicate/overlapping rules** (two rules covering the same technique + logsource with near-identical logic) are not detected by any script in `scripts/` — this is also `detection-content-reviewer` territory, done by inspection, not automated.

### Credential handling
- **Splunk credentials** (`SPLUNK_BASE_URL`, `SPLUNK_USERNAME`, `SPLUNK_PASSWORD`, `SPLUNK_APP`, `SPLUNK_OWNER`, `SPLUNK_VERIFY_TLS`) are injected as GitHub Actions secrets, scoped per-job to a GitHub **environment** — `dev` for `ci_dev_workflow.yml`'s `deploy_to_splunk`/`splunk_verify` jobs, `prod` for `ci_prod_workflow.yml`'s `deploy_to_prod` job. This is a real isolation boundary: a workflow run against `dev` cannot read `prod`'s secret values (and vice versa) purely by referencing `secrets.SPLUNK_*` — GitHub resolves the value from whichever environment the job declares.
- **`SPLUNK_VERIFY_TLS` defaults to `'false'`** (`${{ secrets.SPLUNK_VERIFY_TLS || 'false' }}`, in both the dev deploy/verify steps and the prod deploy step) when the secret isn't set. That means TLS certificate verification against Splunk is opt-in, not opt-out — worth confirming it's actually set to `true` in both environments if the Splunk endpoints are reachable over anything other than a fully trusted private network, since the fallback silently disables verification rather than failing closed.
- **`GH_PAT_DEV_PUSH`** is a personal access token (not the default, auto-scoped `GITHUB_TOKEN`) used for: the initial checkout with push rights in `prepare_validate_convert` and `splunk_verify` (`ci_dev_workflow.yml`), the `gh pr create` call and the `gh project item-add`/`item-edit` calls in `open_promotion_pr`'s `Open promotion PR to main and mark it In review` step (its own separate job, `needs: splunk_verify`, `ubuntu-latest`, no checkout), and the `gh project item-add`/`item-edit` calls in `project_status_automerged.yml`. Using a PAT here (rather than `GITHUB_TOKEN`) is what lets CI push directly to `dev` and manage Project #3 items — both of which need broader scope than the default token grants. This token is a higher-value target than a typical `GITHUB_TOKEN`-scoped secret precisely because of that broader scope; it's worth confirming its actual grant is no wider than "push to this repo + manage this project" if that hasn't been audited recently.
- **Splunk write permissions on deployed saved searches** are set explicitly by every deploy call (`SPLUNK_SHARING=app`, `SPLUNK_PERMS_READ="*"`, `SPLUNK_PERMS_WRITE=admin,ci_deploy_savedsearches`) — read is world-open within the Splunk app, write is restricted to the deploying service account role and admin. This is a deliberate, auditable policy baked into the CI step itself (both `ci_dev_workflow.yml` and `ci_prod_workflow.yml` set it identically), not something that varies per rule.
- **No secrets are read from repo files.** All credentials in `scripts/deploy/deploy_spl_to_splunk.py` and the verify scripts come from environment variables set by the workflow from GitHub Actions secrets — there's nothing in `rules/sigma/*.yml`, `rules/splunk/*.spl`, or `*.meta.json` that could leak a credential if a rule file were made public.

### CI trust boundary: dev proves it, prod trusts dev
- `ci_prod_workflow.yml` does **not** re-run validation, Atomic Red Team tests, or verification — it deploys whatever `.spl` is already on `main` on the assumption that it's identical to what `dev` already tested (the regenerate step is explicitly deterministic re-conversion of already-reviewed source, not a fresh compile of unreviewed input). The actual trust boundary is therefore the **human review of the promotion PR**, not any automated re-check — if that review is skipped or rubber-stamped, an untested or subtly-modified rule could reach prod. Nothing in the current workflow enforces required reviewers on `automated-promotion`-labeled PRs; that would be a branch-protection setting outside `.github/workflows/`, not something visible from the workflow YAML alone.
- The promotion PR is opened with a fixed, non-parameterized title and body (`gh pr create --title "Promote verified detections from dev to main" ...`) and only ever diffs whatever is currently different between `dev` and `main` — there's no per-rule breakdown of what's being promoted baked into the PR body beyond the run ID.

### Project-board automation
- `project_status_automerged.yml`'s trigger condition (`github.event.pull_request.merged == true && contains(..., 'automated-promotion')`) is label-gated, not branch- or title-gated — any merged PR carrying the `automated-promotion` label triggers it, regardless of head/base branch. In practice only the auto-opened `dev`→`main` PR carries that label today, but the workflow itself would also fire for a manually-labeled PR, since GitHub Actions can't distinguish "CI applied this label" from "a human applied this label" from the label name alone.
- **Full lifecycle, both ends automated, both unauthenticated against a `merged`/label check only**: the promotion PR is added to Project #3 with Status `In review` at creation time (`ci_dev_workflow.yml`'s `open_promotion_pr` job, gated purely on `needs.splunk_verify.result == 'success'` — see the platform-quirk note in `pipeline_overview.md` for why it reads the upstream job's `result` rather than a job-level output) and moved to Status `Auto-merged` at merge time (`project_status_automerged.yml`, gated on `merged == true` + the `automated-promotion` label). Both option IDs (`4fdb6324` for `In review`, `be04d00f` for `Auto-merged`) were verified against the live Project #3 field schema (`gh project field-list 3 --owner martonbence`) rather than assumed. There's no third state for a promotion PR that gets closed *without* merging — it stays at `In review` on the board indefinitely, since neither workflow has a step for that path.

## Out of scope (explicitly, not by omission)

- **Security monitoring content correctness** — whether a given Sigma rule's detection logic is actually the right way to catch the technique it claims (that's `detection-content-reviewer`'s judgment-layer job, and ultimately a human call informed by it, not a "threat" to this pipeline itself).
- **The security posture of the Splunk deployment or the monitored environment** — this document is about the CI/CD pipeline that deploys rules, not the Splunk instance's own hardening, the victim/DC hosts' patch level, or the production network these detections are meant to protect.
- **Supply-chain security of pipeline dependencies** (`pyyaml`, `jsonschema`, `sigma-cli`, `pysigma-backend-splunk`, `requests`, third-party GitHub Actions like `actions/checkout`, `actions/upload-artifact`) — that's the `security-scanner` subagent's remit (semgrep, `pip-audit`, GitHub secret scanning), not something re-derived here. See its agent definition for current findings/process.
- **Self-hosted runner host hardening** (`de-lab`, `windows-victim`, `windows-dc`) — these are lab infrastructure whose OS/network configuration isn't visible from this repo's code; nothing here should be read as a statement about their patch level or isolation from other lab systems.

## What's not invented here

This document intentionally does not speculate about threats with no evidence in the code — e.g. it does not claim there's a known injection vulnerability in any script, a specific CVE-worthy dependency, or a concrete instance of credential leakage. Where a risk is described above (e.g. `SPLUNK_VERIFY_TLS` defaulting to disabled, the PAT's actual scope being unverified, no enforced reviewer requirement on promotion PRs), it's phrased as "worth confirming" rather than "this is exploited" — these are configuration points the code makes visible, not confirmed incidents.
