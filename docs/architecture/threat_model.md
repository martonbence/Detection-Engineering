# Threat Model

Scope: this document covers risks in *this repo's own pipeline and detection content* — not the security posture of whatever environment a deployed Sigma/SPL rule is meant to protect. It's grounded entirely in what `.github/workflows/*.yml` and `scripts/` actually do; nothing here is a hypothetical "what a mature detection-engineering shop should also worry about" unless the code shows it's actually a live concern.

## In scope

### Rule quality and false-positive risk
- **Schema validity is enforced; logical soundness is not.** `scripts/validate/validate_sigma.py` gates every rule against `docs/schemas/sigma_schema.json` (Draft-07), but that only checks structure — required fields, correct types, and those enum values that are actually reachable (the `tags` enum and pattern are not: see the ATT&CK-tag bullet below). It does not check whether a `detection:` block's filters reference fields the declared `logsource` would actually produce, whether `falsepositives:` is realistic, or whether a `custom.splunk.raw_query` string is syntactically valid SPL beyond what Splunk itself rejects at deploy time. That judgment layer is explicitly the job of the `detection-content-reviewer` Claude Code subagent, not CI.
- **Pass/Fail is evidence of "the search fired once," not "the rule is good."** `pass_fail_eval.py` confirms a saved search matched events after a specific Atomic Red Team execution. A rule can pass this check and still be too broad (high false-positive rate in real traffic) or too narrow (only catches the exact atomic test's command line, not the technique in general) — the pipeline has no signal for either.
- **MITRE coverage gaps** are measurable (`outputs/reports/mitre_technique_map.json`, `navigator_layer.json`, and the Navigator view in `docs/index.html`) but not enforced — nothing blocks a merge for leaving a tactic uncovered. Coverage-gap analysis is currently a human/`ideation`-agent activity, not a CI gate.
- **A wrong ATT&CK tag used to make the coverage view lie, and is now reported but still not gated** (audit item 4.3). The schema's tactic enum and `^attack\.[Tt]\d{4}(\.\d{3})?$` technique pattern sit beside a free-text `anyOf` branch, so they enforce nothing: `attack.t1059.999`, `attack.t1O59.001` and `attack.defense_evasion` all validate. Worse, `generate_stats.py`'s `extract_techniques()` matches a looser `attack\.t\d+`, so a mistyped technique does not fall out of the report — it is rendered as a badge and a Navigator cell, i.e. published as coverage the repo does not have. `scripts/validate/check_mitre_tags.py` now checks every rule's tags against the committed technique map (unknown technique, revoked sub-technique, malformed tag, unknown tactic, tactic mismatch as errors; undeclared tactic and parent/sub-technique redundancy as warnings). It runs **advisory** in CI — without `--strict`, exit code `0` — deliberately: a wrong tag misfiles a working detection on the matrix rather than breaking it. So the failure mode is narrowed from invisible to visible, not closed. All 27 rules are clean as of its introduction. Note also that the two patterns it reconciles still differ from each other — the schema's and the stats generator's — which is tracked separately as audit item 2.22.
- **Duplicate/overlapping rules** (two rules covering the same technique + logsource with near-identical logic) are not detected by any script in `scripts/` — this is also `detection-content-reviewer` territory, done by inspection, not automated.

### Credibility of the published numbers

This repo's central claim is that its Pass/Fail figures are measured, not asserted. The main risk to that claim is not a false measurement but an **expired** one, so the reporting layer is treated as part of the threat surface:

- **A verdict can outlive the rule it describes.** `pass_fail_eval.py` records a PASS against a specific `rule_version`; nothing re-runs the attack when the rule is later edited. Before this was surfaced, `pass_rate_pct` was `all PASS ÷ all rules`, which meant a rule could be rewritten repeatedly and still contribute its original green result indefinitely — at the time this was addressed, 15 of 27 rules carried verdicts from an older version of themselves, so the published 96% was substantially inherited rather than measured. The mitigation is entirely in `generate_stats.py`: the verdict is treated as **superseded** when the stored `rule_version` no longer matches `compute_rule_version()`'s current answer, such verdicts are dropped from both sides of the pass-rate fraction, and `verification_current_pct` publishes how much of the library the remaining fraction actually speaks for. Note what this does *not* do: it doesn't block anything. `splunk_verify`'s exit code and the promotion gate see only the current run's rules, whose verdicts are current by construction — this is a reporting correction, not a CI gate, so a long-lapsed rule can still sit deployed in prod with nobody stopped by it.
- **A verdict can also simply get too old to mean anything, with nobody touching it.** The version check alone leaves a second way for the number to lie: a library nobody edits, verified by a pipeline that has stopped running, would keep reporting the same green figure forever, because nothing about it ever changes. So a verdict older than `REVIEW_INTERVAL_DAYS` (180, a single global constant — no per-rule or per-severity policy) is treated as **expired** and leaves the pass rate the same way a superseded one does. The two are deliberately one concept: same standing, same remedy, same bucket, different diagnosis — superseded is the certain case (the deployed logic provably isn't what was tested), expired is the probabilistic one (nothing in the rule moved, but telemetry, Splunk configuration and attacker tooling may have). A rule that is both counts as superseded, the stronger claim. As of today `verified_expired` is 0 and every lapsed verdict is superseded, so this half of the rule has never actually fired — its value is that the metric now decays on its own rather than depending on someone noticing.
- **Expiry depends on when the page is read, so the published page and the published badge deliberately disagree over time.** `stats.json` and the README badges are computed against `generate_stats.py`'s clock at build time; `docs/index.html` re-derives the same classification in the reader's browser on every load and overwrites the baked-in overlay values. A months-old page therefore shows a lower, more honest pass rate than the badge generated alongside it. Worth knowing before treating a badge as authoritative for anything time-sensitive: the badge is a snapshot, and nothing refreshes it except another pipeline run.
- **Single-number quoting is the realistic failure mode.** A percentage gets screenshotted, pasted into a slide, or quoted in a chat without its caveat. That's why measurement coverage is published as its own badge (`verification_current_pct`, 44% today) next to Pass Rate (92%) rather than as prose beside it, why the Pass badge counts only current passes, and why the rule browser's Verification doughnut renders `92%` / `Pass Rate` and `12 of 27 current` as one visual unit inside the chart center instead of two separately-quotable figures. The same reasoning drove splitting that doughnut in two: `Evidence` rings the whole library, `Verification` rings only the current verdicts, so the pass rate now describes exactly the slices drawn beneath it rather than a subset the reader has to infer — a single ring holding both dimensions invited summing 26/27 = 96% straight off the chart. These are presentation decisions made for accuracy reasons and should be preserved as such if that overlay or badge row is ever redesigned. The lapse exclusion is applied symmetrically: **Pass** reads `verified_pass_current` and **Fail** reads `verified_fail_current`, so the two counts always describe the same population of rules. That symmetry is itself a correctness property — counting successes and failures over different populations would manufacture an apparent discrepancy between two numbers readers instinctively compare, and would let a lapsed verdict be published as one but not the other. The all-inclusive `verified_pass`/`verified_fail` keys still exist in `stats.json` with unchanged meanings; nothing user-facing quotes them.
- **Version detection is coarse, and errs toward under-claiming.** Both `sigma_to_spl.py::_compute_rule_version()` and `generate_stats.py::compute_rule_version()` derive the version from a `git log --follow` commit count, so a docs-only edit to a rule supersedes its verdict exactly like a rewritten `detection:` block. This can only understate confidence, never overstate it — the safe direction — but it does mean `Superseded` must be read as "not re-measured since the file last changed," not "the logic is known to have changed." The correct fix is an explicit, deliberately-bumped `version:` field in the Sigma YAML plus a CI check that it moved (audit item 3.5).
- **"We couldn't test it" is only distinguishable from "it failed" for atomic rules.** `pass_fail_eval.py`'s NOT_VERIFIED gate is guarded by `if tester == "atomic"`, so it never applies to the 8 rules with `testing.type: emulation`. For those, an emulation test that never ran (or was killed mid-batch) yields zero events and is published as a **FAIL** — a detection-quality claim made on the basis of an infrastructure failure. This is a live accuracy gap in the published numbers, not a hypothetical one (audit item 2.8).

### Credential handling
- **Splunk credentials are mostly *not* environment-scoped, and the isolation is narrower than it looks.** Corrected 2026-08-06 against the repository's actual secret configuration; the previous wording here claimed "a real isolation boundary" between `dev` and `prod`, which overstated it.

  Only **`SPLUNK_APP`** is scoped to the GitHub **environment** (`dev` for `ci_dev_workflow.yml`'s `deploy_to_splunk`/`splunk_verify` jobs, `prod` for `ci_prod_workflow.yml`'s `deploy_to_prod`). `SPLUNK_BASE_URL`, `SPLUNK_USERNAME`, `SPLUNK_PASSWORD` and `SPLUNK_VERIFY_TLS` are **repository** secrets with no environment override, so both environments resolve them to the same values.

  `SPLUNK_APP` is an environment **variable** (`${{ vars.SPLUNK_APP }}`), not a secret — corrected under audit item 2.18. An app namespace is a routing label, not a credential: it authorises nothing on its own, and the only thing secret-masking bought was hiding the value that decides dev-vs-prod from the logs of the job it aims. It is still environment-scoped, so the scoping claim above is unchanged; only the *kind* of setting changed. This does move one point below: the two values are now readable and directly comparable between the `dev` and `prod` environments, which they were not while both were masked secrets — the cross-check the pipeline still lacks is at least now something a human can perform. It is read exclusively from step-level `env:` blocks, after the job's `environment:` has resolved; referencing it from a job-level `if:` would silently yield an empty string (the trap audit item 2.20 hit with `LAB_ONLINE`). If the variable is unset in an environment, every consumer's `env_required()` rejects the empty value and exits non-zero before the first HTTP call, so a missing app name fails the deploy rather than writing into a nameless namespace (`deploy_spl_to_splunk.py` and `check_saved_search_hits.py` exit 1, `wait_for_indexing.py` and `reconcile.py` exit 2).

  The values are `detection_engineering` in the `dev` environment and `prod` in the `prod` one. Note the dev app's *label* in Splunk is `dev` while its directory name is `detection_engineering`, and the REST namespace (`servicesNS/{owner}/{app}/…`) is built from the directory name — so the value that looks right in Splunk's app list is the one that would 404. Worth stating precisely, because this is the string that aims a delete operation (below).

  In other words: **one Splunk server, two apps, one set of credentials.** The separation between dev and prod is Splunk's app namespace and nothing else. That is real for saved-search objects — they are distinct per app — but it does not separate the search head, the indexes, or the account's write access. The service account can write to both apps, and the *only* thing aiming a deploy at one rather than the other is the value of `SPLUNK_APP`.

  The sharpest consequence: `scripts/state/reconcile.py --apply` **deletes** saved searches, and it is aimed by that same value. A wrong `SPLUNK_APP` in the `dev` environment would point a delete operation at production objects. Nothing in the pipeline currently cross-checks that the two environments resolve to different apps.

  One control was added on 2026-08-06 and it narrows the aiming problem without solving it: the `prod` **environment** now carries a deployment branch policy admitting only `main`. What it closes is a specific, reachable accident. `ci_prod_workflow.yml`'s `push` trigger was already pinned to `main`, but audit item 2.5 deliberately gave that workflow a `workflow_dispatch`, and a dispatch can name any ref — so until now the prod deploy could be started from `dev`, resolve `environment: prod`, and push unverified SPL into the production app on a wrong dropdown selection. It no longer starts at all off any other branch.

  What it does **not** close, and should not be read as closing: the Splunk credentials are *repository* secrets, so anyone with write access can add a workflow on any branch that deploys straight to the production app without declaring an environment at all. This control stops the accident, not the adversary. In a single-maintainer lab the accident is the realistic failure mode, which is why it is worth having — but the boundary is exactly that wide and no wider.

  Note also that this rule lives in GitHub's settings, not in the repository. Nothing in a clone records it, no commit changes it, and a `git log` will never show it being removed.

  This is a defensible arrangement for a lab — a second Splunk instance for a personal lab is not a proportionate ask — but it should be stated for what it is rather than described as an isolation boundary it is not.

  On the namespace owner: there **is** a `SPLUNK_OWNER` repository secret, but nothing reads it. `deploy_spl_to_splunk.py` and `check_saved_search_hits.py` both derive the `servicesNS/{owner}/...` owner directly from `SPLUNK_USERNAME`, since there was never a reason for the two to diverge — the secret is a leftover and can be deleted. That simplification alone did not fix every ACL/`.../acl` update failing with "You do not have permission to change the owner of this object", though: confirmed against Splunk's own REST API docs, `.../acl` treats `owner` as a required body parameter, and `set_acl()` was never actually sending it. Omitting it was read by Splunk as an implicit (and rejected) ownership change on every call, regardless of whether the owner was actually moving; the real fix was adding the explicit `owner` field to the payload.
- **`SPLUNK_VERIFY_TLS` no longer fails open, and no longer does it silently** (audit item 2.14, closed 2026-08-06). It used to be referenced as `${{ secrets.SPLUNK_VERIFY_TLS || 'false' }}` at all five call sites — four in `ci_dev_workflow.yml` (deploy, indexing wait, hit query, reconcile) and one in `ci_prod_workflow.yml`. That fallback was not neutrality: it converted a *missing* secret into a positive instruction to skip certificate verification, overriding — one layer up, and invisibly — the `env_bool("SPLUNK_VERIFY_TLS", default=True)` that all four consuming scripts had already resolved the safe way. The `|| 'false'` is gone from all five references, so an unset secret renders empty, `env_bool` falls through to verifying, and the connection either checks the certificate or fails loudly. That is the intended trade: a run that dies on an untrusted certificate is a visible, fixable problem; a run that quietly stops checking is not. Disabling verification for a self-signed lab certificate remains available — it just has to be said out loud by setting the secret to `false`.

  The second half of the item was the silence. None of the four scripts said which mode it was in, so both states looked identical in the logs. Each now prints `TLS certificate verification: on.` or emits a `::warning` annotation naming the risk. `tests/test_tls_verification.py` guards both halves: it requires the `||`-free form at exactly five workflow call sites (and fails if it finds a different number), and asserts all four consumers fail closed on empty, missing and unrecognisable values.

  `SPLUNK_VERIFY_TLS` remains a **repository secret** rather than becoming a variable — an owner's decision, and the reasoning that moved `SPLUNK_APP` does not transfer: it does not need to differ between environments, so nothing is gained by making it comparable across them. Its current value is `true`.
- **`GH_PAT_DEV_PUSH`** is a personal access token (not the default, auto-scoped `GITHUB_TOKEN`) used for: the initial checkout with push rights in `prepare_validate_convert` and `splunk_verify` (`ci_dev_workflow.yml`), and the `gh pr create` call and the `gh project item-add`/`item-edit` calls in `open_promotion_pr`'s `Open promotion PR to main and mark it In review` step (its own separate job, `needs: splunk_verify`, `ubuntu-latest`, no checkout). Using a PAT here (rather than `GITHUB_TOKEN`) is what lets CI push directly to `dev` and manage Project #3 items — both of which need broader scope than the default token grants. This token is a higher-value target than a typical `GITHUB_TOKEN`-scoped secret precisely because of that broader scope; it's worth confirming its actual grant is no wider than "push to this repo + manage this project" if that hasn't been audited recently. (The post-merge `In review` → `Auto-merged` board transition, covered below, does not use this token at all — it's done by Project #3's own native board automation, not by any repo workflow.)
- **Splunk write permissions on deployed saved searches** are set explicitly by every deploy call (`SPLUNK_SHARING=app`, `SPLUNK_PERMS_READ="*"`, `SPLUNK_PERMS_WRITE=admin,ci_deploy_savedsearches`) — read is world-open within the Splunk app, write is restricted to the deploying service account role and admin. This is a deliberate, auditable policy baked into the CI step itself (both `ci_dev_workflow.yml` and `ci_prod_workflow.yml` set it identically), not something that varies per rule.
- **No secrets are read from repo files.** All credentials in `scripts/deploy/deploy_spl_to_splunk.py` and the verify scripts come from environment variables set by the workflow from GitHub Actions secrets — there's nothing in `rules/sigma/*.yml`, `rules/splunk/*.spl`, or `*.meta.json` that could leak a credential if a rule file were made public.

### CI trust boundary: dev proves it, prod trusts dev
- `ci_prod_workflow.yml` does **not** re-run validation, Atomic Red Team tests, or verification — it deploys whatever `.spl` is already on `main` on the assumption that it's identical to what `dev` already tested (the regenerate step is explicitly deterministic re-conversion of already-reviewed source, not a fresh compile of unreviewed input). The actual trust boundary is therefore the **human review of the promotion PR**, not any automated re-check — if that review is skipped or rubber-stamped, an untested or subtly-modified rule could reach prod. Nothing in the current workflow enforces required reviewers on `automated-promotion`-labeled PRs; that would be a branch-protection setting outside `.github/workflows/`, not something visible from the workflow YAML alone.
- The promotion PR is opened with a fixed, non-parameterized title and body (`gh pr create --title "Promote verified detections from dev to main" ...`) and only ever diffs whatever is currently different between `dev` and `main` — there's no per-rule breakdown of what's being promoted baked into the PR body beyond the run ID.

### Project-board automation
- **Full lifecycle, split across two different trust boundaries.** The promotion PR is added to Project #3 with Status `In review` at creation time by repo code (`ci_dev_workflow.yml`'s `open_promotion_pr` job, gated on `always() && needs.splunk_verify.result == 'success'` — see the platform-quirk note in `pipeline_overview.md` for why it reads the upstream job's `result` rather than a job-level output, and why the explicit `always()` is required alongside that check). It's then moved to Status `Auto-merged` at merge time by Project #3's own native, UI-configured board automation ("Pull request merged" → set Status to `Auto-merged`, configured under the Project's own Settings → Workflows) — not by any workflow in `.github/workflows/`. A repo workflow (`project_status_automerged.yml`) previously duplicated this second step from CI, but its run history (checked via the GitHub API) shows it only ever executed once, and that run was skipped — every real promotion has landed on `Auto-merged` via the native Project automation instead, so the redundant workflow file was removed as dead code.
- Both option IDs (`4fdb6324` for `In review`, `be04d00f` for `Auto-merged`) were verified against the live Project #3 field schema (`gh project field-list 3 --owner martonbence`) rather than assumed — that verification is still accurate for the `In review` transition, which remains repo code. The `Auto-merged` transition's own trigger semantics, however, are platform-side Project configuration this repo's code can't see or gate on — there's no label check, branch check, or credential involved from this repo's perspective, since the automation lives entirely in GitHub's Project UI rather than in a workflow file. There's no third state for a promotion PR that gets closed *without* merging — it stays at `In review` on the board indefinitely, since nothing (repo-side or native) transitions it on close-without-merge.

## Out of scope (explicitly, not by omission)

- **Security monitoring content correctness** — whether a given Sigma rule's detection logic is actually the right way to catch the technique it claims (that's `detection-content-reviewer`'s judgment-layer job, and ultimately a human call informed by it, not a "threat" to this pipeline itself).
- **The security posture of the Splunk deployment or the monitored environment** — this document is about the CI/CD pipeline that deploys rules, not the Splunk instance's own hardening, the victim/DC hosts' patch level, or the production network these detections are meant to protect.
- **Supply-chain security of pipeline dependencies** (`pyyaml`, `jsonschema`, `sigma-cli`, `pysigma-backend-splunk`, `requests`, third-party GitHub Actions like `actions/checkout`, `actions/upload-artifact`) — not re-derived here. Two things do cover it elsewhere: `ci_code_checks.yml`'s `dependency_audit` job runs `pip-audit` over both pinned requirements files on every code change (advisory — findings warn, but pip-audit failing to run fails the job), and the `security-scanner` subagent's remit (semgrep, `pip-audit`, GitHub secret scanning) covers the rest. See its agent definition for current findings/process.
- **Self-hosted runner host hardening** (`de-lab`, `windows-victim`, `windows-dc`) — these are lab infrastructure whose OS/network configuration isn't visible from this repo's code; nothing here should be read as a statement about their patch level or isolation from other lab systems.

## What's not invented here

This document intentionally does not speculate about threats with no evidence in the code — e.g. it does not claim there's a known injection vulnerability in any script, a specific CVE-worthy dependency, or a concrete instance of credential leakage. Where a risk is described above (e.g. the PAT's actual scope being unverified, no enforced reviewer requirement on promotion PRs, no cross-check that the two environments resolve to different Splunk apps), it's phrased as "worth confirming" rather than "this is exploited" — these are configuration points the code makes visible, not confirmed incidents.
